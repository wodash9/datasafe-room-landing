# DataSafe Room — Product Strategy, UX y backlog vendible

Actualizado: 2026-05-07

## 1. Resumen ejecutivo

**DataSafe Room** no debe venderse como un dataspace genérico. Debe presentarse como una **sala controlada de colaboración de datos industriales**: un entorno acotado, con finalidad concreta, permisos, trazabilidad, reglas de salida y evidencias, donde cliente y proveedor pueden resolver un caso de negocio sin entregar datos brutos ni abrir sistemas internos de forma indiscriminada.

**Wedge inicial recomendado:** colaboración cliente-proveedor para **PCF / huella de carbono de producto / sostenibilidad de producto**. Es un dolor suficientemente visible para dirección, compras, ESG y supply chain; obliga a pedir datos a proveedores; genera fricción por confidencialidad; y permite demostrar valor con datos sintéticos en pocos días.

**Casos secundarios vendibles:**

- **Data Act readiness:** inventariar datos compartibles/no compartibles, contratos, derechos de acceso, políticas y evidencias de respuesta.
- **Calidad y trazabilidad:** compartir evidencias de lote, no conformidades, certificados, versiones de ficha técnica y auditorías de proveedor.

**Producto vendible en una frase:**

> Convertimos un intercambio sensible de datos industriales entre cliente y proveedor en una sala controlada, trazable y demostrable, empezando por PCF/sostenibilidad y extendiendo a Data Act, calidad y trazabilidad.

## 2. Principios de posicionamiento

### 2.1 Qué sí vender

- Una **sala de colaboración** para un caso concreto, no una plataforma abstracta.
- Reducción de fricción en solicitudes de datos cliente-proveedor.
- Minimización de exposición: compartir indicadores, evidencias y agregados antes que datos brutos.
- Trazabilidad: quién pidió qué, quién aportó qué, cuándo, con qué versión y bajo qué reglas.
- Pilotos controlados con datos sintéticos o extractos no críticos antes de conectar sistemas reales.
- Entregables accionables: demo, mapa de datos, matriz de permisos, flujo de aprobación, informe de gaps y roadmap.

### 2.2 Qué evitar prometer

- “Cumplimiento completo” de Data Act, CSRD, ESRS, DPP, Catena-X o Gaia-X sin revisión legal/sectorial.
- Seguridad absoluta o imposibilidad de fuga.
- Integración automática con ERP/MES/SCADA/PLM en 7 días.
- Marketplace de datos, monetización de datos o federación enterprise desde el primer piloto.
- Sustituir sistemas core del cliente.

### 2.3 Narrativa comercial recomendada

- **Dolor:** “Necesitáis datos de proveedores/clientes, pero nadie quiere enseñar más de lo necesario.”
- **Tensión:** “Excel, email y PDFs no dan control, trazabilidad ni confianza.”
- **Solución:** “Montamos una sala controlada por caso: finalidad, datos mínimos, roles, evidencias, aprobaciones y salida auditada.”
- **Resultado:** “En días/semanas podéis enseñar una colaboración industrial realista sin exponer datos sensibles.”

## 3. ICP e industrias objetivo

### 3.1 ICP primario

**Empresas industriales B2B de 50–1.000 empleados** que venden a clientes medianos/grandes y reciben presión para aportar datos de producto, calidad, sostenibilidad o trazabilidad.

Características:

- Operan con proveedores y clientes recurrentes.
- Tienen datos repartidos entre Excel, ERP, MES, PDFs, emails y carpetas.
- Reciben cuestionarios de clientes sobre emisiones, trazabilidad, sustancias, calidad, certificados o origen.
- Les preocupa revelar recetas, consumos, rendimientos, capacidad, costes, proveedores o know-how.
- Tienen una persona de calidad/sostenibilidad/compras que ya coordina intercambios manuales.
- No quieren un proyecto IT largo antes de ver valor.

### 3.2 Sectores prioritarios

1. **Automoción Tier 2/Tier 3 y componentes industriales**
   - Dolor: PCF, requisitos OEM/Tier 1, trazabilidad, PPAP/APQP, cambios de proveedor.
2. **Packaging, plástico, metal, química ligera**
   - Dolor: composición, reciclado, energía, huella, conformidad, certificados.
3. **Alimentación, agroindustria y piensos**
   - Dolor: lote, origen, auditorías, certificaciones, calidad, trazabilidad.
4. **Maquinaria y mantenimiento industrial**
   - Dolor: fichas técnicas versionadas, repuestos, manuales, evidencias de intervención.
5. **Fabricantes con cadena multi-proveedor**
   - Dolor: consolidación de datos de proveedores y respuestas a clientes grandes.

### 3.3 Compradores y champions

- **Comprador económico:** gerencia, dirección industrial, COO, dirección de operaciones.
- **Champion funcional:** sostenibilidad/ESG, calidad, supply chain, compras, product manager técnico.
- **Gatekeeper:** IT, seguridad, legal/compliance.
- **Usuario frecuente:** responsable de calidad/sostenibilidad/compras que hoy persigue datos por email.

### 3.4 Señales de buen lead

- “Nos piden huella de producto / datos ESG / trazabilidad y cada cliente lo pide diferente.”
- “No podemos enviar consumos, recetas o datos de producción completos.”
- “Tardamos semanas en reconstruir evidencias de lote o proveedor.”
- “Tenemos muchos Excels y PDFs; nadie sabe cuál es la versión vigente.”
- “IT no quiere abrir el ERP/MES para un piloto.”

## 4. Propuesta de valor por caso de uso

### 4.1 Caso principal: PCF / sostenibilidad de producto cliente-proveedor

**Problema:** un cliente pide huella de carbono de producto o datos de sostenibilidad a un proveedor. El proveedor no quiere revelar consumos detallados, recetas, volúmenes, rendimientos o estructura de costes. El cliente necesita evidencias suficientes y trazabilidad de la respuesta.

**Propuesta:** DataSafe Room define una solicitud PCF por producto/lote/familia, recoge datos mínimos y evidencias, calcula o estructura indicadores compartibles, permite aprobación interna y genera una salida auditada para cliente.

**Resultado vendible:**

- Solicitud PCF estructurada.
- Mapa de datos requeridos vs disponibles.
- Indicadores compartibles y campos protegidos.
- Evidencias adjuntas o referenciadas.
- Registro de versiones, aprobaciones y exportación.
- Demo con cliente/proveedor usando datos sintéticos.

### 4.2 Caso secundario: Data Act readiness

**Problema:** empresas con productos/equipos/datos industriales necesitan prepararse para solicitudes de acceso o intercambio de datos, pero no tienen inventario, reglas, propietarios ni flujo de respuesta.

**Propuesta:** DataSafe Room modela una sala de solicitud de datos: qué datos existen, quién puede pedirlos, quién aprueba, qué se entrega, qué se excluye, con qué justificación y qué evidencias quedan.

**Resultado vendible:**

- Inventario inicial de datasets y sensibilidad.
- Matriz de derechos, roles y restricciones.
- Flujo de recepción, evaluación, aprobación y entrega.
- Plantillas de respuesta y registro auditado.
- Gap report no legal: puntos a revisar con legal/IT.

### 4.3 Caso secundario: calidad y trazabilidad

**Problema:** cliente/proveedor necesitan compartir evidencias de lote, certificados, fichas técnicas o no conformidades sin abrir todo el histórico ni enviar carpetas completas.

**Propuesta:** DataSafe Room crea una sala por producto, lote, incidencia o auditoría, con evidencias versionadas, permisos por participante, comentarios, aprobaciones y paquete de salida.

**Resultado vendible:**

- Timeline de lote/proceso/incidencia.
- Evidencias adjuntas con metadatos.
- Certificados y fichas técnicas vigentes.
- Flujo de no conformidad y respuesta proveedor.
- Export audit pack para auditoría o cliente.

## 5. Paquetes comerciales hipotéticos

> Precios como hipótesis para validación; adaptar por sector, alcance, integraciones y madurez del cliente.

### 5.1 DataSafe Room Diagnostic — 7 días

- **Precio objetivo:** 3.000–6.000 €.
- **Cliente ideal:** empresa que quiere ver valor antes de proyecto IT.
- **Alcance:** 1 caso, 1 producto/familia/lote, 2–3 roles, datos sintéticos o muestra anonimizada.
- **Entregables:** mapa de caso, matriz de datos, prototipo navegable/no-code o mock funcional, informe de gaps, propuesta 4–8 semanas.
- **No incluye:** integraciones productivas, cálculo PCF certificado, asesoría legal formal.

### 5.2 PCF Supplier Collaboration Sprint — 4 a 8 semanas

- **Precio objetivo:** 12.000–30.000 €.
- **Cliente ideal:** fabricante/proveedor con presión de cliente grande por datos de sostenibilidad.
- **Alcance:** 1 sala PCF operativa para 1–3 productos/familias y 1–5 proveedores o clientes.
- **Entregables:** flujo de solicitud/respuesta, data intake, indicadores, evidencias, aprobación, audit log, export cliente, roadmap.
- **Upsell:** conectores a ERP/PLM/MES, automatización de formularios proveedor, reporting ESG.

### 5.3 Data Act Readiness Room — 3 a 6 semanas

- **Precio objetivo:** 8.000–20.000 €.
- **Cliente ideal:** fabricante de equipos/productos conectados o proveedor industrial que prevé solicitudes de acceso a datos.
- **Alcance:** 1 familia de datos/equipos, inventario, sensibilidad, reglas y simulación de solicitud.
- **Entregables:** room de respuesta, matriz de acceso, flujo de aprobación, gap report para legal/IT.

### 5.4 Quality and Traceability Room — 4 a 8 semanas

- **Precio objetivo:** 12.000–35.000 €.
- **Cliente ideal:** calidad/operaciones con auditorías, lotes, reclamaciones o documentación dispersa.
- **Alcance:** 1 proceso/línea/producto, evidencias de lote o incidencia, export audit pack.
- **Entregables:** timeline trazable, fichas/certificados versionados, workflow de no conformidad, export.

### 5.5 Managed DataSafe Room — mensual

- **Precio objetivo:** 1.500–5.000 €/mes.
- **Cliente ideal:** organización que ya validó un caso y necesita operación continua.
- **Incluye:** mantenimiento de sala, nuevas plantillas, soporte a usuarios, mejora de reglas, reporting, pequeños conectores.
- **Excluye:** grandes integraciones, certificaciones, asesoría legal especializada.

## 6. Usuarios, roles y permisos

### 6.1 Roles externos e internos

- **Room Owner:** responsable del caso; crea sala, define finalidad, invita participantes, aprueba salida final.
- **Data Provider:** proveedor o equipo interno que aporta datos/evidencias.
- **Data Requester:** cliente o equipo que solicita indicadores/evidencias.
- **Data Steward:** valida calidad, consistencia, metadatos y versiones.
- **Approver:** dirección/calidad/legal/IT que aprueba compartir datos o exportar paquete.
- **Auditor / Viewer:** consulta evidencias y trazabilidad sin editar.
- **Admin IT/Security:** gestiona usuarios, SSO si aplica, políticas base, retención y logs.
- **Consultant / Facilitator:** Black Tower/Etharlia; configura plantillas, guía workshops y prepara demo/informe.

### 6.2 Permisos base

- Ver sala.
- Crear solicitud.
- Subir evidencia.
- Ver evidencia sensible.
- Ver indicadores agregados.
- Comentar.
- Aprobar/rechazar.
- Exportar.
- Administrar participantes.
- Ver audit log.
- Configurar políticas.

### 6.3 Estados de sala

- Borrador.
- Configurada.
- Invitaciones enviadas.
- Recogida de datos.
- Validación interna.
- Pendiente de aprobación.
- Lista para compartir.
- Exportada/cerrada.
- Archivada.

## 7. UX objetivo

### 7.1 Concepto de interfaz

La UX debe sentirse como una **deal room / data room industrial**, no como un BI genérico.

Pantallas principales:

1. **Dashboard de salas**
   - Salas activas, estado, responsable, urgencia, cliente/proveedor, fecha límite.
2. **Room Overview**
   - Finalidad, participantes, reglas, checklist, progreso, próximos pasos.
3. **Data Request Builder**
   - Plantilla PCF/Data Act/calidad; campos requeridos; sensibilidad; evidencias esperadas.
4. **Provider Workspace**
   - Tareas del proveedor, campos a completar, documentos a adjuntar, dudas/comentarios.
5. **Data Review and Quality**
   - Completitud, incoherencias, flags, versiones, validaciones manuales.
6. **Sensitivity and Sharing Rules**
   - Qué se comparte, qué se oculta, qué se agrega, qué requiere aprobación.
7. **Approval Center**
   - Resumen ejecutivo, riesgos, cambios desde versión anterior, aprobar/rechazar.
8. **Audit Pack / Export**
   - Paquete descargable con indicadores, evidencias permitidas, log y disclaimers.
9. **Admin and Templates**
   - Plantillas de sala, roles, campos, políticas y catálogos.

### 7.2 UX principles

- **Caso antes que dato:** empezar por “qué necesitamos resolver” y no por “sube datasets”.
- **Mínima exposición visible:** cada campo debe indicar si se comparte, se agrega, se oculta o queda solo interno.
- **Progreso guiado:** checklist claro por roles.
- **Confianza por trazabilidad:** audit log visible y exportable.
- **Lenguaje industrial:** producto, lote, cliente, proveedor, certificado, evidencia, versión, aprobación.
- **Sin fricción IT inicial:** CSV/Excel/PDF/manual primero; conectores después.

## 8. Journeys clave

### 8.1 Journey A — Cliente solicita PCF a proveedor

1. Room Owner crea sala “PCF Producto X para Cliente Y”.
2. Selecciona plantilla PCF y define finalidad, plazo, producto/familia y nivel de detalle.
3. Sistema genera checklist de datos: materiales, energía, transporte, proceso, factores, evidencias.
4. Data Provider recibe invitación y ve solo sus tareas.
5. Proveedor completa campos, adjunta evidencias y marca datos sensibles.
6. Data Steward revisa completitud y coherencia.
7. Room Owner define salida: indicadores agregados, evidencias permitidas, campos ocultos.
8. Approver revisa riesgos y aprueba exportación.
9. Data Requester recibe paquete o vista controlada.
10. Sala queda cerrada con audit log y versión final.

**Criterios de aceptación:**

- La sala muestra finalidad, producto, participantes, fecha límite y estado.
- Cada dato requerido tiene owner, sensibilidad, estado y evidencia asociada opcional.
- Un proveedor no puede ver datos de otros proveedores salvo permiso explícito.
- La salida final excluye campos marcados como internos/no compartibles.
- El audit log registra creación, cambios, aprobaciones y export.

### 8.2 Journey B — Simulación Data Act readiness

1. Consultant crea sala “Solicitud de acceso a datos — Equipo/Familia Z”.
2. Se inventarian datasets disponibles, propietarios y sensibilidad.
3. Se simula una solicitud de acceso por rol externo.
4. Legal/IT/negocio clasifican qué se entrega, limita o rechaza.
5. Se genera respuesta modelo y gap report.
6. Dirección decide roadmap de políticas, contratos e integraciones.

**Criterios de aceptación:**

- Cada dataset tiene owner, ubicación, tipo, sensibilidad y decisión de compartición.
- El flujo permite justificar entrega/rechazo/limitación.
- El informe separa gaps técnicos, organizativos y legales.
- El producto no afirma cumplimiento legal automático.

### 8.3 Journey C — Sala de calidad/trazabilidad por incidencia

1. Calidad crea sala para reclamación/lote/incidencia.
2. Invita proveedor, producción, calidad interna y cliente si procede.
3. Se agregan evidencias: certificados, fotos, análisis, lote, ficha técnica, acciones correctivas.
4. Se revisan versiones y consistencia.
5. Se aprueba un paquete de respuesta.
6. Se exporta audit pack para cliente/auditoría.

**Criterios de aceptación:**

- El timeline de eventos puede ordenarse por fecha, actor y tipo de evidencia.
- Las evidencias tienen versión, origen y permiso.
- La respuesta final incluye solo evidencias aprobadas.
- Queda registro de quién aprobó y cuándo.

## 9. Features por módulos y criterios de aceptación

### Módulo 1 — Room Setup and Purpose Control

**Objetivo:** crear una sala por caso con finalidad, alcance, reglas y participantes.

Features:

- Crear sala desde plantilla: PCF, Data Act, Calidad/Trazabilidad.
- Definir finalidad, alcance, producto/lote/familia, cliente/proveedor, deadline.
- Invitar participantes y asignar roles.
- Checklist inicial por plantilla.
- Estados y progreso.

Criterios de aceptación:

- Un usuario con permiso puede crear sala en menos de 5 minutos usando plantilla.
- La sala no puede pasar a “Recogida de datos” sin finalidad, owner, participantes mínimos y deadline.
- Cada participante ve solo salas a las que fue invitado.
- El progreso se calcula por tareas completadas/obligatorias.

### Módulo 2 — Data Request and Intake

**Objetivo:** estructurar la solicitud y entrada de datos sin depender de integraciones iniciales.

Features:

- Formulario configurable por plantilla.
- Carga manual, CSV/Excel y adjuntos PDF/imagen.
- Campo de sensibilidad: público de sala, restringido, interno, agregado.
- Owner y estado por campo.
- Comentarios y preguntas por dato.

Criterios de aceptación:

- Cada campo requerido puede marcarse como pendiente, enviado, en revisión, aceptado o rechazado.
- El proveedor puede guardar borrador antes de enviar.
- El sistema conserva versiones al modificar un dato enviado.
- Los adjuntos quedan vinculados a un campo, evento o evidencia.

### Módulo 3 — Sensitivity, Policies and Sharing Rules

**Objetivo:** controlar qué se comparte y cómo se transforma antes de salir.

Features:

- Clasificación de campos por sensibilidad.
- Reglas de salida: compartir exacto, compartir rango, agregar, anonimizar, ocultar.
- Vista previa “lo que verá el cliente/proveedor”.
- Bloqueo de export si hay campos sensibles sin decisión.
- Plantillas de políticas por caso.

Criterios de aceptación:

- Ningún campo marcado “interno” aparece en export externo.
- El usuario puede previsualizar la salida por rol antes de aprobar.
- Exportar requiere que todos los campos incluidos tengan decisión de compartición.
- Cambios en reglas quedan registrados en audit log.

### Módulo 4 — Evidence and Traceability

**Objetivo:** gestionar evidencias, versiones y trazabilidad de decisiones.

Features:

- Biblioteca de evidencias por sala.
- Metadatos: origen, fecha, owner, tipo, versión, permiso, caducidad.
- Timeline de eventos.
- Relación evidencia ↔ dato ↔ aprobación ↔ export.
- Audit log inmutable a nivel funcional.

Criterios de aceptación:

- Toda evidencia tiene owner, fecha y permiso por defecto.
- El timeline muestra creación, edición, comentarios, aprobaciones y exportaciones.
- Un export puede reconstruirse con las versiones exactas usadas.
- El audit log no puede editarse desde la interfaz estándar.

### Módulo 5 — PCF / Sustainability Workspace

**Objetivo:** resolver el caso principal de sostenibilidad de producto.

Features:

- Plantilla PCF por producto/familia/lote.
- Campos: materiales, energía, proceso, transporte, embalaje, factor de emisión, periodo, supuestos.
- Indicadores: completitud, cobertura de evidencias, incertidumbre cualitativa, versión.
- Resultado compartible: resumen PCF, metodología declarada, evidencias permitidas.
- Disclaimer de no certificación salvo validación externa.

Criterios de aceptación:

- El usuario puede completar un caso PCF sintético de extremo a extremo.
- El resultado distingue datos aportados, estimados y pendientes.
- El export incluye supuestos/metodología y no afirma certificación.
- Los datos sensibles pueden agregarse u ocultarse en la vista cliente.

### Módulo 6 — Data Act Readiness Workspace

**Objetivo:** preparar flujos de solicitud y respuesta de acceso a datos.

Features:

- Inventario de datasets por producto/equipo/proceso.
- Clasificación: personal/no personal, industrial sensible, secreto comercial, contractual, técnico.
- Simulación de solicitud por actor.
- Decisión: entregar, limitar, rechazar, requiere revisión legal.
- Gap report y roadmap.

Criterios de aceptación:

- Cada dataset inventariado tiene owner, ubicación, sensibilidad y decisión.
- La respuesta simulada incluye justificación y evidencias.
- El informe advierte que no sustituye revisión legal.
- Se puede exportar un gap report ejecutivo.

### Módulo 7 — Quality and Traceability Workspace

**Objetivo:** compartir información de calidad/lote/incidencia de forma controlada.

Features:

- Sala por lote, incidencia, auditoría o ficha técnica.
- Timeline de lote/proceso/no conformidad.
- Evidencias: certificados, fotos, análisis, fichas, órdenes, acciones correctivas.
- Control de versiones de ficha técnica/certificado.
- Export audit pack.

Criterios de aceptación:

- Una incidencia puede contener eventos, evidencias y acciones correctivas.
- Las fichas/certificados muestran versión vigente y anteriores.
- El audit pack excluye documentos no aprobados.
- Cliente externo ve solo el paquete autorizado.

### Módulo 8 — Collaboration and Workflow

**Objetivo:** reducir coordinación por email y aumentar responsabilidad.

Features:

- Tareas por rol.
- Comentarios por dato/evidencia.
- Solicitud de aclaración.
- Notificaciones por email o resumen manual en MVP.
- SLA/deadline y semáforos.

Criterios de aceptación:

- Cada tarea tiene responsable, fecha, estado y vínculo a dato/evidencia.
- Un usuario puede pedir aclaración sin cambiar el dato original.
- El Room Owner ve bloqueos y pendientes por participante.
- Las acciones relevantes quedan en audit log.

### Módulo 9 — Approval and Export

**Objetivo:** que nada salga sin revisión y que el paquete final sea defendible.

Features:

- Resumen ejecutivo para aprobación.
- Comparación de cambios desde última versión.
- Aprobación/rechazo con comentario obligatorio.
- Export PDF/ZIP/CSV según paquete.
- Marca de versión y fecha.

Criterios de aceptación:

- Exportar requiere aprobación si la política de sala lo exige.
- Un rechazo devuelve la sala a revisión con motivo visible.
- El export contiene versión, fecha, participantes, alcance y disclaimers.
- El sistema conserva histórico de exports.

### Módulo 10 — Admin, Security and Governance

**Objetivo:** dar confianza suficiente sin sobredimensionar el MVP.

Features:

- Gestión de usuarios y roles.
- Políticas de retención por sala.
- Configuración de plantillas.
- Registro de actividad.
- Opcional futuro: SSO, MFA, DLP, cifrado por tenant, conectores.

Criterios de aceptación:

- Admin puede revocar acceso de un usuario.
- El usuario revocado no puede abrir sala ni exports internos.
- Las plantillas pueden duplicarse y ajustarse sin desarrollo.
- Logs básicos son exportables para revisión.

  - Aceptación: paquete final no incluye campos internos.
- **P1-06 — Gap report y roadmap automático/manual**
  - Generar informe con datos faltantes, riesgos y próximos pasos.
  - Aceptación: informe exportable tras piloto.
- **P1-07 — Onboarding de proveedor**
  - Invitación simple, guía de tareas, vista limitada.
  - Aceptación: proveedor completa datos sin formación larga.

### P2 — Diferenciación y escalado

- **P2-01 — Conectores CSV/Excel robustos**
  - Mapeo de columnas, validaciones, import recurrente.
- **P2-02 — Integraciones ERP/PLM/MES selectivas**
  - Solo tras validar caso y con alcance cerrado.
- **P2-03 — Motor de reglas avanzado**
  - Rangos, agregación, anonimización, reglas por cliente/proveedor.
- **P2-04 — Multi-supplier campaign**
  - Enviar solicitud PCF a muchos proveedores y consolidar estado.
- **P2-05 — Indicadores de calidad de datos**
  - Completitud, consistencia, frescura, evidencia, incertidumbre.
- **P2-06 — Portal externo de consulta**
  - Cliente ve paquete autorizado sin descargar todo.
- **P2-07 — SSO/MFA y hardening enterprise**
  - Requisitos de clientes mayores.
- **P2-08 — Plantillas sectoriales**
  - Automoción, packaging, alimentación, maquinaria.

### P3 — Plataforma / dataspace avanzado

- Catálogo de data products compartibles.
- Contratos/políticas machine-readable.
- Federación entre organizaciones.
- APIs de acceso controlado.
- Interoperabilidad con estándares sectoriales.
- Certificaciones/auditorías externas, si el mercado lo justifica.

## 11. MVP 7 días

### Objetivo

Cerrar una demo y oferta vendible, no construir plataforma completa.

### Alcance

- 1 caso PCF/sostenibilidad.
- 1 cliente, 1 proveedor, 1 consultor, 1 approver.
- Datos 100 por ciento sintéticos o anonimizados.
- UX en Figma, web estática, Airtable/Notion/Retool, mock o app mínima.
- Export mock PDF/ZIP opcional.

### Plan de 7 días

- **Día 1 — Caso y guion**
  - Definir industria ficticia, producto, solicitud PCF, roles, riesgos y narrativa.
- **Día 2 — Dataset sintético**
  - Crear datos de materiales, energía, transporte, evidencias y campos sensibles.
- **Día 3 — UX demo**
  - Pantallas: dashboard, room overview, provider workspace, review, sharing rules, approval, export.
- **Día 4 — Reglas y auditabilidad**
  - Sensibilidad, salida autorizada, log de eventos y versiones.
- **Día 5 — Paquete comercial**
  - One-pager, propuesta, pricing, exclusiones, preguntas de discovery.
- **Día 6 — Demo rehearsal**
  - Ensayar guion de 10 minutos y preparar objeciones.
- **Día 7 — Validación**
  - Enseñar a 3–5 contactos o grabar walkthrough; recoger feedback.

### Definition of Done 7 días

- Se puede explicar el producto sin decir “dataspace” en la primera frase.
- Demo end-to-end enseña solicitud, aporte, sensibilidad, aprobación y export.
- Hay 3 paquetes con pricing hipótesis.
- Hay lista de 20 leads y email/outbound script.
- Está claro qué NO incluye el piloto.

## 12. MVP 4–8 semanas

### Objetivo

Operar un piloto real o semi-real con un cliente y producir un audit pack defendible.

### Alcance recomendado

- 1 tenant/cliente.
- 1–3 productos/familias o lotes.
- 1–5 proveedores/clientes externos.
- Formularios configurables.

- Reglas de salida.

### Semana 1–2 — Discovery y configuración

## 13. Métricas de producto y negocio

## 14. Demo sintética recomendada

### Escenario

**Empresa cliente:** IberAuto Systems, fabricante Tier 1 ficticio.

**Proveedor:** MetalPart Norte, Tier 2 ficticio que fabrica una carcasa de aluminio.

**Caso:** IberAuto solicita PCF y evidencias de sostenibilidad de la carcasa `AL-HOUSING-42` para responder a un OEM. MetalPart puede compartir huella agregada y evidencias, pero no quiere revelar consumo energético por línea, rendimiento, scrap exacto ni coste de material.

### Datos sintéticos

- Producto: `AL-HOUSING-42`.
- Periodo: Q1 2026.
- Material: aluminio reciclado/primario con porcentajes aproximados.
- Energía: consumo total agregado por lote o familia, no por máquina.
- Transporte: distancia proveedor-cliente y modo.
- Evidencias: factura energética ficticia, certificado ISO ficticio, ficha técnica versionada, declaración de proveedor de material.
- Campos sensibles: rendimiento de línea, scrap exacto, coste €/kg, proveedor de aleación, consumo por máquina.
- Salida permitida: PCF estimado/agregado, rango de energía, porcentaje reciclado aproximado, evidencias no confidenciales.

### Pantallas a enseñar

1. **Landing / mensaje**
   - “Sala controlada para colaboración de datos industriales.”
2. **Dashboard**
   - Sala PCF con estado “Pendiente de proveedor”.
3. **Room Overview**
   - Finalidad, participantes, deadline, checklist.
4. **Vista proveedor**
   - Tareas a completar, campos sensibles marcados, evidencias adjuntas.
5. **Sensitivity Rules**
   - Exacto vs agregado vs oculto; preview de vista cliente.
6. **Review**
   - Completitud, flags, datos estimados, evidencias.
7. **Approval Center**
   - Qué se va a compartir y riesgos.
8. **Export / Audit Pack**
   - Resumen PCF, evidencias permitidas, log, disclaimers.
9. **Gap Report**
   - “Qué falta para pasar de demo a piloto real.”

### Guion de demo de 10 minutos

- Min 0–1: dolor cliente-proveedor y por qué email/Excel falla.
- Min 1–2: creación de sala con finalidad concreta.
- Min 2–4: proveedor aporta datos y marca sensibilidad.
- Min 4–6: reglas de salida y preview de lo que verá el cliente.
- Min 6–8: aprobación, export y audit log.
- Min 8–10: paquete piloto, tiempos, límites y siguientes pasos.

## 15. Qué enseñar a cliente

### En primera llamada

- Problema y caso concreto, no arquitectura.
- Demo sintética de PCF cliente-proveedor.
- Matriz simple: dato requerido / sensibilidad / salida permitida.
- Antes/después: email+Excel vs sala controlada.
- Paquete Diagnostic de 7 días.

### En reunión con dirección

- Valor económico: menos tiempo, menos riesgo, respuesta más rápida a clientes.
- Riesgo controlado: mínimo dato, permisos, aprobaciones, trazabilidad.
- Roadmap: empezar con PCF y extender a Data Act/calidad.
- Precio y alcance cerrado.
- Decisiones necesarias: caso, sponsor, usuarios, datos no críticos.

### En reunión con IT/seguridad

- Boundary claro: piloto sin tocar sistemas críticos al inicio.
- Datos sintéticos/anonimizados o extractos controlados.
- Roles y permisos.
- Retención y export.
- Conectores solo en fase posterior.
- Lista de no-promesas y supuestos.

### En reunión con calidad/sostenibilidad/compras

- Checklist de datos y evidencias.
- Cómo se reducen emails y persecución manual.
- Cómo se responde a cliente/proveedor con versión y aprobación.
- Cómo se reutiliza la sala para próximos productos/proveedores.

## 16. Discovery comercial: preguntas clave

### Para PCF/sostenibilidad

- ¿Quién os pide datos de sostenibilidad y con qué frecuencia?
- ¿Qué formato os piden: Excel, portal, PDF, cuestionario, estándar sectorial?
- ¿Qué datos os da miedo compartir?
- ¿Cuánto tardáis en responder hoy?
- ¿Qué evidencias necesitáis adjuntar?
- ¿Quién aprueba antes de enviar?
- ¿Qué parte del proceso es más manual o conflictiva?

### Para Data Act readiness

- ¿Qué datos generan vuestros productos/equipos/procesos?
- ¿Quién podría pedir acceso a esos datos?
- ¿Tenéis inventario y owners?
- ¿Qué datos son sensibles por secreto comercial, contrato o seguridad?
- ¿Cómo responderíais hoy a una solicitud?

### Para calidad/trazabilidad

- ¿Cuánto tardáis en reconstruir un lote/incidencia?
- ¿Dónde viven certificados, fichas y evidencias?
- ¿Cómo controláis versiones vigentes?
- ¿Qué compartís con cliente y qué queda interno?
- ¿Qué auditorías o reclamaciones os consumen más tiempo?

## 17. Riesgos y mitigaciones

- **Riesgo: vender demasiado abstracto.**
  - Mitigación: abrir siempre con PCF/calidad/Data Act, no con dataspace.
- **Riesgo: alcance de integración explota.**
  - Mitigación: MVP manual/CSV primero; conectores como upsell.
- **Riesgo: cliente espera cumplimiento legal.**
  - Mitigación: disclaimers; colaboración con legal externo si se requiere.
- **Riesgo: datos reales demasiado sensibles.**
  - Mitigación: sintéticos/anonimizados; reglas de salida; piloto local.
- **Riesgo: proveedor no colabora.**
  - Mitigación: UX simple, tareas claras, beneficio para proveedor: control sobre qué comparte.
- **Riesgo: PCF exige metodología/certificación.**
  - Mitigación: posicionar como colaboración y trazabilidad de datos PCF, no certificador.

## 19. Recomendación final

La estrategia más vendible es convertir DataSafe Room en una **oferta productizada de bajo riesgo**:

1. **Entrada:** Diagnostic de 7 días con demo y mapa de datos.
2. **Producto inicial:** PCF Supplier Collaboration Room en 4–8 semanas.
3. **Expansión:** Data Act readiness y Quality/Traceability Rooms.
4. **Retención:** Managed DataSafe Room mensual.

El mensaje central debe ser: **“No os pedimos abrir vuestros sistemas ni compartir datos brutos; os damos una sala controlada para responder a clientes/proveedores con mínima exposición y trazabilidad.”**
